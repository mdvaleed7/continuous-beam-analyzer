## Fix 1 — BEAM-FEM-001: Tapered-beam FEM cantilever moment formula

### Issue
`getTaperedBeamNormalizedFEM` in `beamEngine.ts` computed the cantilever
fixed-end moment for a trapezoidal load as:

```ts
const M_cant = -(2 * wL_val + wR_val) * L * L / 6;
```

This is the moment of the trapezoidal load about the FREE (right) end of the
cantilever, NOT about the FIXED (left) end. The cantilever fixed-end support
moment is the moment of the load about the FIXED end.

### Cause
For a trapezoidal load with intensity `wL` at the fixed end and `wR` at the
free end, the moment of the load about the FIXED end is:

```
M_left = ∫₀ᴸ w(ξ)·ξ dξ
       = ∫₀ᴸ [wL·ξ + (wR − wL)·ξ²/L] dξ
       = wL·L²/2 + (wR − wL)·L²/3
       = L²·(wL + 2·wR)/6
```

The previous formula `L²·(2·wL + wR)/6` is the moment about the FREE end
(`∫₀ᴸ w(ξ)·(L−ξ) dξ`). The two coincide for UDL (`wL = wR = w` gives `wL²/2`
both ways), so Set A's regression tests (which use UDL) all passed — but for
any non-uniform trapezoidal load on a tapered beam the FEM was incorrect.

The wall engine feeds trapezoidal earth-pressure loads (different intensities
at top and bottom of each segment) through this path for tapered walls, so
the bug affected wall designs with non-UDL pressure on tapered thicknesses.

### Reference
- Standard structural analysis (cantilever fixed-end moment = moment of load
  about the fixed end).
- Cross-checked against the closed-form uniform-beam branch in the same
  function (`d2 ≈ d1`): for triangular load with peak at the fixed end, the
  closed-form gives `M_left = −wL²/20` (textbook FEM for fixed-fixed beam),
  which the corrected Simpson's-rule branch now matches.

### Files Modified
- `src/components/beamEngine.ts`

### Code Changes
```diff
-    const M_cant = -(2 * wL_val + wR_val) * L * L / 6;
+    const M_cant = -(wL_val + 2 * wR_val) * L * L / 6;
```
Plus an extensive derivation comment block explaining the correct formula
and the three sanity checks (UDL, triangular peak-at-fixed, triangular
peak-at-free).

### Validation
New tests in `src/__tests__/audit2026Fixes.test.ts`:

1. **UDL on (near-)uniform tapered beam matches closed-form** — `M_left ≈ −wL²/12`,
   `M_right ≈ +wL²/12`, `V_left ≈ V_right ≈ −wL/2` ✓
2. **Triangular load (peak at fixed end) matches closed-form `wL²/20`** —
   `M_left ≈ −wL²/20`, `M_right ≈ +wL²/30`, `V_left ≈ −7wL/20`,
   `V_right ≈ −3wL/20` ✓
3. **Triangular load (peak at free end) matches closed-form `wL²/30`** —
   `M_left ≈ −wL²/30`, `M_right ≈ +wL²/20`, `V_left ≈ −3wL/20`,
   `V_right ≈ −7wL/20` ✓
4. **Buggy formula gave WRONG `M_left` (regression guard)** — confirms the
   two formulas disagree for non-UDL trapezoidal load on a tapered beam,
   and that the corrected value approaches the textbook FEM as `d2 → d1`.

End-to-end tests in `src/__tests__/audit2026EndToEnd.test.ts` verify the
wall engine's vertical equilibrium (Σ reactions = Σ loads) for:
- Uniform wall with UDL+surcharge pressure (1% tolerance)
- Tapered wall with triangular pressure (2% tolerance — Simpson's rule)
- Multi-zone wall with partial water table (10% tolerance)

## Fix 2 — RW-XBAR-001: Retaining-wall resultant position

### Issue
`analyzeRetainingWall` computed the resultant position as:

```ts
const x_bar = SigmaV > 0 ? M_resisting / SigmaV : 0;
```

This is the centroid of the VERTICAL forces only. The lateral (overturning)
forces, which shift the resultant toward the toe, were ignored.

### Cause
The standard retaining-wall resultant formula (Reynolds's Reinforced Concrete
Designer's Handbook §8.3.2, IS 1904 bearing-pressure eccentricity check)
is:

```
x_bar = (M_resisting − M_overturning) / ΣV
```

The previous formula `M_resisting / ΣV` is only correct when `M_overturning = 0`
(no lateral load). For any wall with active earth pressure, the overturning
moment is non-zero and shifts the resultant toward the toe (reducing x_bar).

The previous formula gave an x_bar that was too large (resultant too close
to the heel), causing under-estimation of toe pressure and over-estimation
of heel pressure — unsafe for stem, heel and toe flexure design.

### Reference
- Reynolds's Reinforced Concrete Designer's Handbook §8.3.2 (resultant of
  vertical + lateral forces on a retaining wall).
- IS 1904 bearing-pressure eccentricity check.
- Any standard textbook on retaining-wall design.

### Files Modified
- `src/components/retainingWallEngine.ts`

### Code Changes
```diff
-    const x_bar = SigmaV > 0 ? M_resisting / SigmaV : 0;
-    // Net moment about the centroid:
-    const M_net = SigmaV * x_bar - M_overturning; // = M_resisting - M_overturning about toe, then shift
-    // Simpler: resultant x measured from centroid = x_bar - B/2
-    const eccentricity = x_bar - B_m / 2;
+    const x_bar = SigmaV > 0 ? (M_resisting - M_overturning) / SigmaV : 0;
+    // Eccentricity measured from the base centre, POSITIVE TOWARD HEEL.
+    //   x_bar < B/2  →  resultant on toe side  →  e < 0  →  toe pressure higher
+    //   x_bar > B/2  →  resultant on heel side →  e > 0  →  heel pressure higher
+    const eccentricity = x_bar - B_m / 2;
```

### Validation
New tests in `src/__tests__/audit2026EndToEnd.test.ts`:

1. **`x_bar` includes overturning moment** — confirms
   `r.eccentricity ≈ (M_resisting − M_overturning)/ΣV − B/2`, NOT
   `M_resisting/ΣV − B/2`.
2. **No-lateral-load degenerate case** — for `phi = 89°` (Ka ≈ 0, no
   surcharge), `M_overturning ≈ 0` and the corrected formula reduces to
   `M_resisting / ΣV`.

## Fix 3 — RW-PBEAR-001: Bearing-pressure sign convention

### Issue
The bearing pressure at the toe and heel had the `±6e/B` signs reversed
relative to the eccentricity convention used:

```ts
// OLD (wrong):
const p_toe  = p_avg + p_avg * (6 * eccentricity / B_m) * 1;
const p_heel = p_avg - p_avg * (6 * eccentricity / B_m);
```

With `eccentricity = x_bar − B/2` (positive toward the heel), the correct
formulas are:

```ts
// CORRECTED:
const p_toe  = p_avg - p_avg * (6 * eccentricity / B_m);  // toe LOWER when e>0
const p_heel = p_avg + p_avg * (6 * eccentricity / B_m);  // heel HIGHER when e>0
```

### Cause
The Meyerhof / IS 1904 bearing-pressure distribution for an eccentric load
on a strip footing is:

```
p(x) = (ΣV/B)·(1 + (6·e/B)·(1 − 2·x/B))    (x measured from TOE)
```

where `e` is positive toward the HEEL. At `x = 0` (toe) this reduces to
`p_toe = (ΣV/B)·(1 − 6e/B)`, and at `x = B` (heel) to
`p_heel = (ΣV/B)·(1 + 6e/B)`.

The previous code had the signs of the `±6e/B` terms reversed. When the
resultant was on the toe side (the typical retaining-wall case where
`e < 0`), the code reported the heel pressure as the larger value —
physically backwards. This propagated into the heel and toe flexure
designs (which interpolate the bearing pressure at the stem faces),
causing under-design of both.

### Reference
- Meyerhof bearing-pressure distribution for eccentrically-loaded footings.
- IS 1904 (General structure in foundations) — bearing pressure check.
- Reynolds's Reinforced Concrete Designer's Handbook §8.3.2.

### Files Modified
- `src/components/retainingWallEngine.ts`

### Code Changes
```diff
-    const p_toe = p_avg + p_avg * (6 * eccentricity / B_m) * 1; // toe side (e positive → toe pressure higher)
-    const p_heel = p_avg - p_avg * (6 * eccentricity / B_m);
+    const p_toe = p_avg - p_avg * (6 * eccentricity / B_m);  // toe (front) — LOWER when e>0 (resultant on heel)
+    const p_heel = p_avg + p_avg * (6 * eccentricity / B_m); // heel (back, under soil) — HIGHER when e>0
```

The same sign correction was applied to the interpolated pressures used by
the heel and toe flexure designs:

```diff
-    const p_at_stem_back = p_avg + p_avg * (6 * eccentricity / B_m) * (1 - 2 * x_stem_back / B_m);
+    const p_at_stem_back = p_avg - p_avg * (6 * eccentricity / B_m) * (1 - 2 * x_stem_back / B_m);
...
-    const p_at_stem_front = p_avg + p_avg * (6 * eccentricity / B_m) * (1 - 2 * B_toe_m / B_m);
+    const p_at_stem_front = p_avg - p_avg * (6 * eccentricity / B_m) * (1 - 2 * B_toe_m / B_m);
```

### Validation
New tests in `src/__tests__/audit2026EndToEnd.test.ts`:

1. **Resultant on toe side → `p_toe > p_heel`** (typical retaining-wall
   case) — confirms the corrected signs produce the physically-correct
   distribution.
2. **Bearing pressures match Meyerhof formula** — verifies
   `p_toe = p_avg·(1 − 6e/B)` and `p_heel = p_avg·(1 + 6e/B)` numerically.
3. **Both pressures stay non-negative** — no tension at either edge for a
   stable wall.
4. **Wide-heel case → `p_heel > p_toe`** — confirms the sign convention
   handles the opposite case (resultant on heel side) correctly too.

## Fix 4 — WS-D-001: Waffle-slab rib effective depth

### Issue
`analyzeWaffleSlab` hardcoded the rib effective depth as:

```ts
const d = D - cover - 10; // effective depth
```

The `10` corresponds to a 20 mm bar (half-bar deduction). The actual rib
tension bar diameter is user-selectable via `rib_bar_dia` (default 16 mm)
and is used everywhere else in the engine (Ast, shear, Annex C T-beam
deflection via `tBeamDeflection`).

### Cause
Inconsistency between the Ast-calculation `d` (hardcoded 10 mm deduction)
and the deflection-check `d` (computed from the actual `rib_bar_dia`).
For a 16 mm rib bar (the default), the Ast calc used
`d = D − cover − 10` but the deflection check used `d = D − cover − 8`.
For a 25 mm rib bar (allowed by the optimizer), the Ast calc used
`d = D − cover − 10` (over-estimating d → under-estimating Ast), which
is **un-conservative**.

### Reference
- IS 456 Cl. 23.1 (effective depth = extreme compression fibre to centroid
  of tension steel).
- IS 456 Cl. 26.4.1 (bar placement: clear cover + bar dia/2 to centroid).

### Files Modified
- `src/components/waffleSlabEngine.ts`

### Code Changes
```diff
-    const d = D - cover - 10; // effective depth
+    const ribBarDiaForDepth = input.rib_bar_dia || 16;
+    const d = D - cover - ribBarDiaForDepth / 2; // effective depth (rib tension steel)
```

### Validation
TypeScript compiles cleanly (`tsc --noEmit` → 0 errors). All 23 jest tests
pass. The waffle-slab engine now uses a consistent effective depth across
the Ast calculation, the shear check, and the Annex C T-beam deflection
check.

## Fix 5 — FS-D-001: Flat-slab effective depth

### Issue
`analyzeFlatSlab` hardcoded the slab/drop effective depth as:

```ts
const d_slab = D - cover - 10; // assuming 10mm bar and using avg depth
const d_drop = hasDrop ? (dropDepth - cover - 10) : d_slab;
```

The comment said "10mm bar" but the `10` is the half-bar deduction for a
20 mm bar — a 10 mm bar would use `5`. The actual column-strip bar
diameter is user-selectable via `bar_dia` (default 12 mm) and is used by
the deflection check.

### Cause
Same kind of inconsistency as Fix 4: the Ast / punching-shear calc used
a hardcoded 10 mm deduction while the deflection check used the actual
`bar_dia` (default 12 mm). For a 25 mm column-strip bar (allowed by the
optimizer), the Ast calc would over-estimate `d` and under-estimate Ast.

### Reference
- IS 456 Cl. 23.1 (effective depth).
- IS 456 Cl. 31.2.1 (flat-slab minimum thickness).
- IS 456 Cl. 31.6.3.1 (punching shear critical section at `d/2` from face —
  the `d` here is the effective depth to the tension steel).

### Files Modified
- `src/components/flatSlabEngine.ts`

### Code Changes
```diff
-    const d_slab = D - cover - 10; // assuming 10mm bar and using avg depth
-    const d_drop = hasDrop ? (dropDepth - cover - 10) : d_slab;
+    const flatSlabBarDia = input.bar_dia || 12;
+    const d_slab = D - cover - flatSlabBarDia / 2;
+    const d_drop = hasDrop ? (dropDepth - cover - flatSlabBarDia / 2) : d_slab;
```

### Validation
TypeScript compiles cleanly. All 23 jest tests pass. The flat-slab engine
now uses a consistent effective depth across the punching-shear, flexure,
and deflection checks.

## Fix 6 — WS-ASTMIN-001: Waffle-slab rib minimum steel

### Issue
`analyzeWaffleSlab` computed the rib minimum steel using the SLAB rule:

```ts
const p_min = getMinSteelRatio(fy);
const Ast_min = p_min * (bf_m * 1000) * D_eq;
```

`p_min` is the slab minimum ratio (0.12% for Fe500 per IS 456 Cl. 26.5.2.1),
applied to the flange width × equivalent thickness. This is the wrong rule
for a rib.

### Cause
IS 456 Cl. 30.5.3 explicitly states:

> "Ribs shall be designed as beams in accordance with 26.5.1."

IS 456 Cl. 26.5.1.1(a) (beams) gives:

```
Ast_min = (0.85 / fy) × bw × d
```

For Fe500, this is `0.0017 × bw × d`. The slab rule gave
`0.0012 × bf × D_eq`, which is typically LARGER than the beam rule
(because `bf` is the flange width, much larger than `bw`), so the previous
formula was conservative but not code-compliant.

The fix takes the **maximum** of the beam rule and the slab rule on the
equivalent section — this brings the formula into code compliance while
preserving the previous conservative behaviour for any rib where the slab
rule previously governed.

### Reference
- IS 456:2000 Cl. 30.5.3 (ribs designed as beams).
- IS 456:2000 Cl. 26.5.1.1(a) (beam minimum steel).
- IS 456:2000 Cl. 26.5.2.1 (slab minimum steel — kept as a floor).

### Files Modified
- `src/components/waffleSlabEngine.ts`

### Code Changes
```diff
-    // Min steel for rib (based on equivalent thickness D_eq of voided slab)
-    const p_min = getMinSteelRatio(fy);
-    const Ast_min = p_min * (bf_m * 1000) * D_eq;
-    if (!Number.isNaN(Ast_req)) Ast_req = Math.max(Ast_req, Ast_min);
+    const Ast_min_beam = (0.85 / fy) * bw * d;            // IS 456 Cl. 26.5.1.1(a) — beams
+    const Ast_min_slab = getMinSteelRatio(fy) * (bf_m * 1000) * D_eq; // IS 456 Cl. 26.5.2.1 — slabs
+    const Ast_min = Math.max(Ast_min_beam, Ast_min_slab);
+    if (!Number.isNaN(Ast_req)) Ast_req = Math.max(Ast_req, Ast_min);
```

### Validation
TypeScript compiles cleanly. All 23 jest tests pass. The waffle-slab rib
minimum steel is now code-compliant with IS 456 Cl. 30.5.3 / 26.5.1.1(a),
while preserving the previous conservative behaviour (the slab rule is
kept as a floor via `Math.max`).
